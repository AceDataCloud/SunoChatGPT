# Production release gates

2026-10-18. This repository implements the App-specific adapter and component; it is not a deployed service and cannot connect a real Ace account yet.

1. The existing authorization owner must implement/register the proposed profile-specific read grant (see profiles/*/profile.json) and issue RS256 access tokens bound to this exact `/mcp` resource, subject, tenant, exp/iat and jti. Tokens must live at most five minutes. This repository verifies signatures/issuer/audience/lifetime/scope; it does not create an authorization server or bypass the existing consent/PKCE flow.
2. The existing platform owner must implement an authenticated internal readback endpoint taking `{task_id,subject,tenant_id,token_jti,service,task_api,action:"retrieve"}`. It must atomically enforce authoritative task ownership, tenant and deletion, check jti revocation before every read, reject all write/generate/delete actions, and resolve only existing tasks via existing Ace code. It returns an internal envelope including `owner_subject`, `tenant_id`, authoritative `service`, and stored original `model` for shared image stores; this adapter defensively checks both again. No such public Ace endpoint is claimed here. Missing adapter config fails closed.
3. Current `mcp:access` / Global OAuth MCP credentials are too broad for this release. Restricting an API path alone is insufficient where that path also supports delete. Do not expose platform-wide service tokens to ChatGPT.
4. Decide authoritative `user_id` versus `actor_user_id` semantics with the task owner. No new admin/shared/historical-task exception is introduced by this repository. Missing ownership means reject.
5. Production origin, MCP resource audience, JWKS, exact CSP/widget domain and internal adapter are configured and reviewed. Current CSP has no external connect/resource domains and no media playback. The app binds loopback until a separately approved deployment is configured.
6. Validate revocation, cancellation, consent, issuer discovery and callback with an existing approved account; no account duplication or agreement acceptance by automation.
7. Read full current App submission and media/digital service policy; resolve third-party naming/logo/rights, similarity of independent listings and connection to paid external music service. The canonical pages were network-blocked in this session. The official GitHub checklist is preparation guidance, not legal/policy clearance. No rule is invented to prohibit or approve five listings.
8. Existing policy: https://platform.acedata.cloud/documents/privacy. Public rendered version, App data flow, logs, retention/deletion and support ownership must match implementation; see privacy-data-inventory.md.
9. Reviewer must see actual ChatGPT installation, authorize, read owned task, handle unauthorized IDs, terminal status and permitted media. Current tests use loopback + synthetic identities. No current runtime screenshot, listing ID, original bill verification or acquisition result exists.

Public source dependency handoff (no changes made): MCPs shared/oauth.py / generated suno/core/oauth.py; AuthBackend scope/token/revocation files to be confirmed by its owner; Gateway app/controller.py and app/utils/api_allowlist.py; effective Suno task route/persistence under PlatformService; Backend docs/privacy.md. No migration 2116 change.

## 0.2.0 independent service profiles

The shared engine has five profiles, each exposing one brand-specific tool/resource/scope; no public combined profile. The trusted adapter must select the existing task API from a server-maintained allowlist and enforce the requested profile against the original stored task service/model. It must not trust labels created by this client or a model. Existing Suno envelopes now require `service:"suno"` too. GPT Image requires original `gpt-image-` family, Nano Banana original `nano-banana` family. Profile-only identity must never gain another service's read scope or task. Each deployment needs an exact separate resource audience/origin. No scopes or adapter were changed in production.

Four additional profiles are actual runnable MCP App candidates, not submitted platform Apps. Full independent/similar-App and brand policy remains unknown after official page HTTP403; this uncertainty gates publication, not internal implementation.
